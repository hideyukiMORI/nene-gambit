# ADR 0005 — 画面は 1 文字 1 桁の格子で、盤は 1 升 3 桁、HUD の文言は ASCII の英語

- 状態: 受理（決定 3 のポーンの字形を ADR 0013 で置き換えた）
- 日付: 2026-10-25
- Issue: #5
- 影響する規則: ARC-011 / SWF-014 / FR-07 / FR-10 / FR-12

## 文脈

指示書: 「駒記号は日本語ロケールの端末で East Asian Ambiguous（全角にも半角にもなる）扱いになり、盤がずれる。だから既定は英字。
記号を出すときも、1 マスの桁数を 1 か所で決め、幅の前提を ADR に書く」「色は Render の配色表だけが持つ」。
施主の答え（2026-10-25）: Q4＝英字と駒記号を起動オプションとキーの両方で切り替える / Q5＝HUD に直近の棋譜・通算の勝敗と局数・
手番と手数・白黒の性格名 / Q8＝1 テーマから。

## 決定

1. Render の出力は `Grid`（`Cell` の 2 次元配列）で、**1 つの `Character` が 1 桁を占める**と前提する。Terminal はこの前提で差分を書く
2. 盤は **1 升 3 桁 × 1 行**（`" K "`）。幅を決めるのは `TableRenderer.squareWidth` の 1 か所
3. 駒の字形は `GlyphSet` の 2 組だけ: 英字（`K Q R B N P`・既定）と駒記号（U+265A〜U+265F の塗りつぶしの字形）。
   白と黒は字形ではなく**色**で分ける（英字は大文字のまま、駒記号も白黒とも塗りつぶし）。細い線の字形（U+2654〜U+2659）は端末で見えにくいので使わない
4. **HUD の文言は ASCII の英語**（`Game 12` / `White 3  Black 2  Draws 6` / `White to move, move 23` / `1-0  White wins by checkmate`）。
   全角の文字（2 桁）や幅の曖昧な文字（`·` 等）を入れると、1 文字 1 桁の前提が崩れて HUD と盤がずれる。文言のリテラルは `Wording` だけが持つ
5. 色は `Theme.wood` の 1 つだけ（木目調）。色の値を持つのは `Theme` だけ（Terminal は受け取った `Rgb` を 24 ビットか 256 色の番号にするだけ）
6. 棋譜の表記は SAN（`MoveNotation`）。HUD には直近 4 行（1 行に白黒 1 手ずつ）を出す
7. 盤と HUD がちょうど入る大きさは 67×15。それより小さければ 1 行の文言（`Terminal too small (need 67x15)`）だけを出して待つ

## 強制

- **planned**: 文言のリテラルが `Wording` の外に無いこと・色の値が `Theme` の外に無いこと（字句検査はまだ無い。Render の中の文字列リテラルを数える検査を、規則 ID を付けて足すかは手順 3 の後で決める）
- 1 文字 1 桁の前提が崩れていないかは、施主が Windows Terminal で見て確かめる（Phase 3 の手順 3・QLT-013）。機械では確かめていない

## 結果

- 全角の HUD を作らないので、文字幅の計算（East Asian Width の表）を持たずに済む
- 🔴 駒記号（U+265A〜）自体が East Asian Ambiguous なので、端末の設定によっては 2 桁で描かれて盤がずれる。既定を英字にしたのはこのため。
  記号を選んだときの見え方は手順 3 で確かめる
- 🔴 HUD を英語にしたのは実装側の判断であり、施主の答えではない（Q5 は「何を出すか」で、言語は聞いていない）。手順 3 で施主に確かめる
- 失うもの: 日本語の HUD。必要になったら、文字幅を 1 か所で数える型を Render に足す ADR を書く

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| 1 升 2 桁 | 盤が縦長に見える（端末の文字は縦が横の約 2 倍）。3 桁なら升がほぼ正方形になる |
| 日本語の HUD（全角） | 全角の桁数の計算と、Ambiguous の文字を避ける規則が要る。手順 2 の縦切りに必要ない |
| 白は細い線の駒記号・黒は塗りつぶし | 細い線の字形は端末の文字の大きさでは潰れて見えにくい。白黒は色で分ける |
| 駒記号を既定にする | 指示書と施主の決定（Q4）。英字が既定 |
